### Spawn system (`SpawnManagerGlobal`)

Budget-based, inspired by Vampire Survivors:
- `base_budget_per_second × difficulty_multiplier` accumulates each frame. `base_budget_per_second` is a **fixed** calibration value; `difficulty_multiplier` is runtime state (starts `1.0`, grows `+difficulty_increase_per_minute` per minute, capped at `max_difficulty_multiplier`) — so the *effective* rate is the product, and the base you set never changes on its own.
- When budget ≥ `minimal_budget`, spawns enemies until it drops **below `minimal_budget`** (not to zero: the remainder carries over), at most 10 per frame (`max_spawns_per_frame`, local to `try_spawn_enemies()`) and never above `max_enemies`. Each enemy is a weighted random pick (`spawn_weight`) among those inside their `min_game_time`/`max_game_time` window whose `spawn_cost` fits the current budget.
- **`initial_spawn_delay`** (0.5 s, a plain `var` on the autoload, not exposed in `SpawnManagerConfig`): budget and difficulty accumulate during it, but neither teleport nor spawn run. It counts only while `SPAWN_CLOCK` is free (see *Brief holds*).
- **`initial_budget`** — the budget the match *starts* with (set to `spawn_budget` in `start_spawning()`, so it also re-applies on restart). One-shot: consumed once, then the normal rate resumes; it does not touch the base rate or difficulty. It is a **general "how full is the opening" knob**, not just a burst tool — any value `> 0` shortens the wait for the first spawn; `≥ minimal_budget` crosses the threshold immediately for an opening burst. Calibrated per stage on the `SpawnManagerConfig` instance.
- Positions found via **grid sampling** of 4 rectangular bands around the viewport (N/S/E/W strips), clustered by flood-fill, then filtered to offscreen-only.
- **The spawn point is drawn PER POINT, never per cluster.** `find_spawn_position()` flattens every offscreen cluster into one list, shuffles it, and takes the first point that validates. Picking a cluster first gave a 1-point corridor the same odds as a 300-point plaza, and — worse — when that single point failed, the whole attempt was lost (~15 aborts per session). Shuffling and taking the first valid point is *exactly* a uniform draw among the valid points, so proportionality costs nothing: no weights to compute. It is also what `prepare_safe_teleport_cache()` already did; the two paths now agree. Measured after the change: **zero aborts**, and 1–2 points examined in the overwhelming majority of spawns (worst case 10, out of 270 candidates).
  - Precisely, each **grid point** gets one ticket, not each navigable cell: with `nav_snap_radius ≥ grid_sample_spacing`, neighbouring grid points can snap onto the same cell and it enters the list twice. That weights open ground over slivers — desirable, but it is why `Candidatos` can exceed the cell count.
- **Denser sampling does NOT relieve enemy crowding — this is geometry, not calibration.** An enemy blocks a disc of radius `min_distance_between_enemies`, which is at least as large as any sane spacing (both 32 by default), so halving the spacing quadruples the points *and* quadruples the points inside each blocked disc: the rejected **fraction** is unchanged. Spacing helps against the *wall* filter (finding thin corridors), never against the *enemy* filter. The only two levers that actually open room in a dense horde are a wider spawn band (`spawn_margin_max_*`) and a smaller `min_distance_between_enemies`.
- **The grid scan is cached** (`get_navigable_grid()` — always call this, never `scan_navigable_grid()` directly). Walkable ground and walls are **static**: the result only changes when the *camera* moves, so it is reused until the camera travels more than `GRID_CACHE_MOVE_THRESHOLD` (or the spacing changes). That threshold is a **fixed distance, deliberately independent of `grid_sample_spacing`**: it used to be "half a cell", which tied scan *frequency* to grid *resolution*, so halving the spacing doubled the scans per second **and** quadrupled the points in each. What sets the tolerance is how far the spawn band may lag and still serve. The cheap offscreen filter still runs fresh on every call, so a stale band never approves an invalid point — but staleness is not free either: the *leading* edge of the band goes under-sampled while the player advances, biasing spawns **behind** them. Now that a scan is ~10× cheaper, keep this value low; the saving it buys is no longer needed. **Grid refresh is camera-driven and lazy, never on a clock** — a standing player triggers zero rescans, and this is deliberately a different mechanism from the teleport's periodic sweep (see *Teleport system*): the grid answers "where is valid ground around the camera?" (changes only with the camera), the teleport answers "has anyone drifted too far?" (changes with time).
- **`nav_snap_radius` and `grid_sample_spacing` are coupled — never tune one alone.** The snap is what lets a coarse grid see thin corridors, so coverage is complete only while `nav_snap_radius > grid_sample_spacing × 0.707` (the half-diagonal, i.e. the farthest any position can sit from its nearest grid node). Above that ratio, halving the spacing buys **no new coverage** — only 4× the points and redundant candidates; below it, the band develops blind spots that no other setting compensates. This is why spacing is the first knob to concede when the frame budget tightens, and freshness (the cache threshold) the last.
- **Navigability is read from the TILES, never from `NavigationServer2D`.** `get_snapped_navigable_point()` resolves "is this walkable ground?" through `TileData.get_navigation_polygon()` — the very data Godot uses to *build* the navmesh — and snaps the grid point to the nearest navigable cell within `nav_snap_radius`. **This is the fix for a ~40 ms/scan stutter**: `TileMapLayer` creates **one navigation region per tile** (3762 in stage01, ~7500 triangles) and `map_get_closest_point()` searches them **linearly**, so each call cost ~140 µs — 288 points per scan blew the frame budget twice over. Reading the tile is a hash lookup. Equivalence was verified empirically by running both methods side by side: **zero verdict divergences over 27 scans**.
  - **The decision is PER TILE, never per layer.** A layer like `TileMapBuildings` legitimately mixes collision tiles and navigation tiles; only tiles carrying a navigation polygon are accepted. This is a pattern any stage may use, not a feature of one stage: a building exists twice in the same layer, with back tiles carrying collision and front tiles (z 4) carrying navigation, so enemies can be born and walk behind it (`TileMapBuildings`, `TileMapTech`). Layers whose TileSet has no navigation layer at all (decoration) are dropped wholesale, for free. A point is navigable if **any** consulted layer has a navigable tile there — the same **union** semantics the navigation server applies. What *blocks* is collision, still checked by the (cheap, ~2 µs) physics query at the end.
  - Which layers are consulted comes from **one place only**: `SpawnManagerConfig.enemy_spawn_excluded_layers` (Inspector) — an **exclusion** list. The scene is always swept and every layer with navigation is eligible, **minus** the listed ones; empty (the normal case, no warning) = no exclusion. It used to be an **inclusion** list (`enemy_spawn_ground_layers`: "only these layers spawn"), and that shape was dangerous: a new layer forgotten off the list dropped out of spawn and teleport **silently** — exactly what nearly happened when a new tile layer was introduced, since stage01's list was filled. Inverted on purpose, so that forgetting shows up on screen (enemies spawning where they shouldn't) instead of hiding. The list governs **both spawning and teleport destinations** (the teleport draws from the same ground grid). The autoload keeps the resolved result as `SpawnManagerGlobal.enemy_spawn_ground_layers` (the ground that remains), which is a result, not the Inspector list. What this list controls is **where enemies are BORN or ARRIVE by teleport, never where they can WALK** — movement comes from the navmesh, which never touches it. So excluding a layer here removes it from spawn while enemies keep pathing through it; blocking *movement* is a different tool (the TileSet's navigation-layer bitmask vs the agent's `navigation_layers`).
  - **A `null` entry in that array is always an error, never a choice** — either a slot was added and left unassigned, or the layer was **deleted**; without a check the game would run silently without the intended exclusion. (Renaming or reparenting does *not* break it: the editor rewrites every `NodePath` in the scene automatically. Only deletion — or hand-editing the `.tscn` with Godot closed — leaves a null. Word the warning accordingly, or it teaches the wrong lesson.) `initialize_spawn_manager()` counts unresolved entries and warns with the count, and also warns if the exclusions leave no layer at all. The console prints the resolved ground and the excluded layers on every stage start.
  - This replaced a three-rung cascade (export → `NavigableTileMap` group → sweep) whose two configurable paths produced the same two behaviours, so "marking" felt like an empty ritual — and its name promised navigability while it actually decided spawn ground. The group is gone; do not reintroduce it.
  - `_get_nav_layer_data()` **pre-computes** a `Dictionary` of navigable cells per layer, because the raw per-cell lookup still cost ~25 µs/point (a 5×5 neighbourhood × N layers). Tiles are static; call `invalidate_nav_layer_cache()` if a future stage mutates tiles or `nav_snap_radius` at runtime.
  - **The snap returns the CENTRE of the winning cell, never a point on its edge.** Two separate decisions: *which* cell wins is still decided by distance to the cell **rectangle** (measuring to centres instead would shrink the effective `nav_snap_radius` by up to half a tile diagonal and drop reachable border cells); *what position* is returned is the centre. Clamping into the rectangle — which both this and the old `map_get_closest_point` did — dropped every point coming from outside exactly **on the tile boundary**, i.e. as close to the neighbouring wall as geometrically possible. That was the systematic cause of enemies spawning glued to walls. The centre is by definition the point furthest from that cell's edges, and in a one-tile corridor it is the corridor's centre line. Double gain: better placement **and** more approved points, since `is_safe_from_walls()` runs *after* the snap — narrow corridors gain candidates that used to be rejected for wall proximity.
  - **Approximation, declared:** a tile whose navigation polygon covers only part of the tile is treated as the whole tile. The physics query and the spawn clearance check cover the residue — no risk of spawning inside a wall.
  - **Orphan cells:** `get_used_cells()` can return cells whose `source_id` no longer exists in the TileSet (source removed after painting). Calling `get_cell_tile_data()` on those raises a C++ error, so the source is validated first; the cells are skipped and reported once with their coordinates. This surfaced one real stray cell in `stage01` that had been invisible for months.
- **This scan reads tiles and is independent of the navmesh.** The navmesh has since been collapsed into a single baked region (see *NavmeshMerger*), which fixed the same linear scan on the pathfinding side; the two systems still share nothing but the tile data they both read. The merge is built from **positive** geometry (the walkable tiles) — never Godot's subtractive `NavigationRegion2D` bake ("everything in the rect minus the colliders"), which would turn deliberate map openings into navmesh and make a single forgotten collision tile a silent leak.
- **The validated point IS the body centre — placement and validation speak of the same point.** `spawn_enemy()` writes `enemy.global_position = spawn_pos − _get_body_offset(enemy)`, so the scene origin (the FEET) lands *below* the point and the `BodyCenter` lands exactly *on* it; `check_and_teleport_distant_enemies()` does the same. Both wall clearance and enemy spacing then measure directly at `pos`, with no correction anywhere. **The historical scheme put the FEET on the point** and corrected only the *validation* by an offset — which was incoherent with everything else: the `NavigationAgent2D` is a child of `BodyCenter`, so what traverses the navmesh while the enemy walks is the **body**, and an enemy born feet-on-point started its first navigation frame with its body off the navmesh and got yanked ~10 px. There was also no guarantee the body landed on navigable ground at all — only that no wall was there.
  - **The offset comes from the enemy scene's `BodyCenter` node, never from a copied field** (`SpawnManager._get_body_offset()` reads `marker.position`). There used to be a `body_center_offset` field on `EnemySpawnData` duplicating that node by hand; the two drifted (Red Gator's resource left at the default while its `BodyCenter` was at `−15`), placing the body in the wrong spot with nothing on screen to show it. Reading the node removed the duplicate **and** the guard that existed only to police it. This works because `add_child()` runs before the position is written, so the marker already exists. Missing marker → offset `Vector2.ZERO` (feet on the point, the old behaviour); the warning is not duplicated here because `EnemyBase._validate_scene_setup()` already reports a missing `BodyCenter` once per scene.
- **Per-enemy spawn fit**: wall clearance uses the chosen enemy's own `spawn_clearance_radius` from `EnemySpawnData`'s `Spawn Fit` group, so small enemies spawn in corridors that large ones can't. Clearance slightly below the collider radius is a legal calibration: it allows ~1-3px wall overlap that physics gently resolves on the first frame (used to raise density in tight corridors); going much lower risks depenetration ejecting the enemy through thin walls.
  - **`spawn_clearance_radius` has a structural floor of `tile size ÷ 2` — below it the filter is simply OFF, and every value in that range behaves identically.** The snap returns the **centre** of a navigable cell, so a spawn point is always half a tile from the nearest neighbouring cell's edge: with 16px tiles that is 8px, and any clearance `≤ 8.0` can never reject anything. This is not a defect and the floor is **not** enforced in code — a value below it is a legitimate "filter off, accept the small overlap" choice (stage01's Gator sits at `7.0` against a real collider radius of `10`), so a guard would fire on a correct configuration, which this project's guards must never do. Nor is `8.0` a project constant: it is derived from the TileSet, and a stage with 32px tiles would have a floor of 16. **Measured:** at `7.0` the wall filter rejected ~0 points per cycle; at `10.0`, ~10. Know the floor, do not police it.
  - **Wall clearance is the ONLY thing `spawn_clearance_radius` controls.** It does not move the enemy and it does not affect enemy spacing.
  - **The "no enemy definition" case uses `SpawnManager.FALLBACK_WALL_CLEARANCE`, a `const` — not a knob.** It was an `@export min_distance_from_walls` on both `SpawnManager` and `SpawnManagerConfig` (26.0 in stage01) that **never had any effect**: `_get_min_spawn_clearance()` uses it as the *seed of a search for the minimum*, so any value above the smallest enemy's clearance is discarded — it read like a floor and behaved like a ceiling that never binds. Being in the Inspector is what made it look calibratable. A safety net for "which enemy is this?" is not per-stage data, so it belongs in the script as a constant.
- **Wall clearance is per enemy; enemy spacing is global — and they are not two halves of one setting.** `min_distance_between_enemies` answers "will this look like one enemy materialising on top of another?", not "does the body fit?" (that is the wall check plus the physics). It is measured **BodyCenter to BodyCenter**, on both sides — the same frame as the wall check for that same point, and the project-wide convention. It used to be feet-to-feet, justified as "both sides in the same frame": internally consistent and geometrically wrong, since it compared two **ground shadows** while the wall test for the same point already measured at the body. Between enemies of equal height both give the same number (which is why the error never surfaced); between different heights the error is the difference of the two BodyCenters — 5px between gator (`−10`) and red gator (`−15`), but 22px between a tall enemy (`−30`) and a short one (`−8`), enough to approve an overlapping spawn. Its floor is the physical contact distance of the **largest** enemy (sum of the two collider radii); at that floor two of them spawn exactly tangent, which is legal but leaves zero margin — the value has to be revisited the day a bigger enemy exists. A per-enemy version would not express this correctly either, since the right distance depends on **both** bodies: the principled form is the sum of the two radii, not one value per enemy.
  - **The live body positions are cached per physics frame** (`_get_enemy_body_positions()`), like the enemy list itself, and invalidated at the same two sites — reading `get_body_center_position()` per candidate per enemy would otherwise run thousands of times in a teleport frame.
- **The live enemy list is cached per physics frame** (`_get_enemies()`), because `is_safe_from_other_enemies()` runs >100× in a teleport frame and `get_nodes_in_group()` allocates a fresh Array every call. Deaths are covered by the consumer's `is_instance_valid()`, but **births must invalidate the cache explicitly** — `spawn_enemy()` does this right after `add_child()` — because one frame can spawn several enemies and the second must "see" the first, or `min_distance_between_enemies` silently stops applying within a burst.
- **No silent fallback**: if no offscreen point passes full validation, `find_spawn_position()` returns `Vector2.ZERO` and the spawn is skipped this frame (budget is retained). Never spawn on a rejected point — that was the historical source of enemies inside walls.
- **Teleport system**: every `teleport_check_interval` seconds, enemies too far from the player are recycled into the spawn area. Two-phase validation: the cache is pre-filtered with the **smallest** clearance among defined enemies (so tight-corridor points exist in it), then `_take_position_fitting_enemy()` re-validates each candidate with the specific enemy's own clearance at assignment time. That second step checks walls only: enemy spacing is validated when the cache is built, so enemies teleported in the same cycle are not checked against each other. **Order matters:** the cheap per-enemy distance check runs *first*, and the expensive cache preparation only happens if someone actually qualifies — otherwise a full grid scan+validation was paid every cycle and thrown away.
  - **The cache is sized by demand, and validated lazily.** `prepare_safe_teleport_cache(needed)` shuffles the **candidate points** (a swap, free) and validates one by one until it has `needed + MAX_TRIES_PER_ENEMY - 1` approved — it used to validate *every* offscreen point to consume at most 10, and the discarded fraction grew with the horde (`is_safe_from_other_enemies` walks every live enemy per point) precisely when the frame was tightest. Shuffling the candidates instead of the approved list is what keeps the distribution random while stopping early. `needed` is `enemies_to_teleport.size()`, **not** `max_teleports_per_frame` — that export is only its ceiling, so raising it scales this automatically. If the pool runs out before the target, the cycle ends with a smaller cache — the pre-existing "cache esgotado" path, never worse than the old behaviour. Measured in play: 80–90% of points skipped on low-demand cycles, 50–65% on full-demand ones, 0% (identical to before) in tight areas where the pool is exhausted.
  - **That target is derived, not calibrated — it is exactly what the batch CAN read.** `_take_position_fitting_enemy()` tests at most `MAX_TRIES_PER_ENEMY` positions from the **end** of the array, and a rejection removes nothing (only the accepted one is taken), so the reading window slides down by one per successful teleport and the lowest index anyone in the batch reaches is `n − MAX_TRIES_PER_ENEMY − (needed − 1)`. Everything below that is validation thrown away. The leftover `MAX_TRIES_PER_ENEMY - 1` positions are **not** slack: they are where a Red Gator finds its second option after rejecting a spot a Gator would fit. **Invariant, checkable from the log:** a cycle that teleports its whole demand ends with `Cache restante` at exactly `MAX_TRIES_PER_ENEMY - 1`; any other number means the formula and the consumer have diverged. This replaced a pair of constants — a linear ×3 margin and a floor of 16 — that computed this same number in every real case, except that the ×3, being linear, demanded *more* validation the fuller the horde: at a demand of 38 it asked for 114 approved points from a band holding 118, sweeping the whole band in the tightest frame of the session. **For a future, much larger enemy the first lever is still free: teleport the biggest first**, so it picks from a full cache.
  - **`_take_position_fitting_enemy()` validates at `pos`, never `pos + offset`.** The cache holds body-centre points, so adding the offset there tested the wall 10px (gator) or 15px (red gator) above where the collider would sit. It was a leftover of the feet-based placement that the spawn path had already been converted away from — what varies per enemy is the **clearance**, never the point.
  - **A debug path must validate exactly like the production path.** `validate_teleport_position_debug()` was checking walls with a global wall distance while production used `_get_min_spawn_clearance()` — so **turning the log on made the filter stricter** and produced a session full of "cache vazio" that never happens in play. A whole round of analysis was spent on symptoms that only the instrument created. When a debug variant of a function exists, it may add *reporting*, never a different *criterion*.
  - **`max_teleports_per_frame` is a queue ceiling, and too low a ceiling shows up as drift, not as a stall.** At 10 the backlog never cleared and enemies wandered past 1,100 px before their turn came; at 50 the same run never exceeded ~680 px, with no measurable cost — moving an enemy is free, validating points is what costs. Raising it further is safe on the cache side — the target now grows by one point per extra enemy, not by three.
- **Teleport distance is per-axis** (`max_distance_from_player_horizontal` / `_vertical`), tested as a **rectangle** — an enemy qualifies when it passes the limit on *either* axis. It is measured BodyCenter to BodyCenter, like the other spawn distances. A single radial distance fits this game badly: the viewport (and therefore the spawn band) is much wider than tall, so one value is always too tight on one axis and too loose on the other. **Calibration rule:** each axis must exceed that axis's outer spawn edge (half-viewport + its `spawn_margin_max_*`), or enemies spawn already eligible for teleport; the surplus above that edge is how far they may wander before being recycled.
- `SpawnManagerConfig` calls `SpawnManagerGlobal.start_spawning()` by itself, one frame after its own `_ready()` (`auto_start`, default on); `stop_spawning()` runs on every scene change (done by `_end_current_scene()`).
- **Per-stage spawn calibration**: `enemy_definitions` is configured as **embedded resources** on the `SpawnManagerConfig` instance inside each stage scene (e.g. in `stage01.tscn`'s scene tree) — never on the base `spawn_manager_config.tscn`, whose default must stay empty (setting it there would leak into every stage). Embedded entries keep each stage's calibration independent. Empty slots in the `enemy_definitions` array are safely ignored by `choose_enemy()`.
- **`max_enemies` is per-stage and intentionally unsettled.** Each stage will get its own value, tied to its level design, and no project-wide ceiling is planned. So never treat the current number as a target, never hardcode a horde size, and never phrase a performance conclusion as "the game handles N enemies" — express it as fixed cost + cost per enemy (see Performance budget) and let each stage pick where to stop.
