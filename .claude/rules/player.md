### Player

- **`scripts/player_base.gd`** — `CharacterBody2D` base class: FSM (idle/walk/attack/dead), movement, `take_damage()`, flash effect, audio.
- **Concrete player scenes** live in `entities/players/` and **normally share the same script `scripts/player_character.gd`** (extends `PlayerBase`), differing only by Inspector calibration and assets. A new character normally needs **no new script**: build the scene, point its root at `player_character.gd`, and calibrate. Two layers, not three: `PlayerBase` (FSM, input movement, damage, audio — scene-agnostic) → `player_character.gd` (wires the concrete nodes, flip + `facing_direction`, the visual FSM, and the attack cycle whose duration comes from `anim.get_animation(...).length`). Unlike enemies, players have **no divergent archetypes** — every player walks by input and attacks via `AttackController` — so a third layer only appears if a future player diverges in *logic* (a dash, a transformation), never merely in art: animations are driven by **name and time** (`current_animation_position`), never by frame index, so a player with a different frame count shares the same script untouched. Named for its **role** (`player_character`), not for a mechanism (`player_animated` would age badly the moment a player animates differently).
- **The player is CREATED AT RUNTIME by `entities/stage_parts/player_spawner.tscn` (`scripts/player_spawner.gd`) — never placed by hand in a stage.** Root is a **`Marker2D`**: here the node's transform **is** the data (it marks where the player appears), unlike `NavmeshMerger`, which is also `Node2D` but whose position is ignored. Not an `Area2D` — it detects nothing, it is read; the swap chamber is what detects (see *Chambers*). Creation itself lives in the static `PlayerSpawner.spawn(scene, at, from)` (`class_name PlayerSpawner`), shared by this spawner and the chamber, so one place decides how a player enters the world.
  - **Which character comes from `PlayerRosterGlobal`, with a two-state override on the instance.** Cascade: the spawner's `forced_player` export (filled) → `PlayerRosterGlobal.get_selected_player()` → `PlayerRosterGlobal.DEFAULT_PLAYER`. **Empty `forced_player` is the normal case, not an omission** (same discipline as `enemy_spawn_excluded_layers`); filling it means *this stage imposes this character* — a tutorial, an intro, a stage scripted around one character.
  - **It adds the player to the `YSortContainer`, resolved by group**, exactly as `SpawnManagerConfig` resolves the enemy parent. If no container is found, the fallback puts the player in the spawner's own parent and warns: there the player is not Y-sorted against the enemies, and who covers whom follows tree order for the whole match. **Keep the spawner itself outside the container:** it adds the player there during its own `_ready()`, and Godot normally refuses `add_child()` on a parent that is still setting up its children.
  - **It refuses to spawn if the `Player` group is already occupied**, with a warning — the net against leaving a hand-placed player in a stage, which would give two players and silently break every system that resolves the player by group.
  - **Tree order: it is normally the first child of the stage, but this is a convention, not a requirement.** `SpawnManagerConfig` and `LoadoutBar` wait one frame before looking up the `Player` group, and the camera keeps looking for the player every frame, so none of them depends on it. Only a node that looks up the `Player` group in its own `_ready()` would have to come after this one. If the player does not exist when spawning starts, `start_spawning()` fails loudly (`push_error`, spawn never enabled).
- **`PlayerRosterGlobal` is a separate autoload, NOT a variable in `GameStateGlobal`, and the criterion is LIFETIME.** `GameStateGlobal` holds *match* state (health, the FSM) and its `_end_current_scene()` is the single place that clears cross-session state. Nothing in the roster may be cleared: dying and restarting must not change your character, and unlocks will go to a save file. Keeping it there would work today and leave the trap of whoever next adds to that cleanup having to remember *not* to clear those lines. Named for the **role** (the roster) — `PlayerSelection` would age badly the day unlocks land.
  - **API:** `select_player(scene)` (written by the chambers; emits `selected_player_changed`), `get_selected_player()` (never null — falls back to `DEFAULT_PLAYER`), `is_selected(scene)` (compares by `resource_path`, so it does not depend on both references coming from the same cache).
  - **The chosen character is a `PackedScene`, and that is the whole identity — there is NO integer ID system, and none is planned.** `player_character.gd` is shared by every character, so no code needs to know *which* player. `attack_id` exists because **three** things must agree (`AttackData` ↔ `AttackUpgradeData` ↔ timer); nothing here needs joining like that. Saving to disk would need the `uid://` **string**, still not an int, and a per-character `PlayerData` resource (name, portrait, locked state) would *replace* an ID system rather than require one.
- **A player swap at runtime is only legal in a scene with NO enemies.** `EnemyBase` caches the player's `BodyCenter` **node** and `SpawnManagerGlobal.player` is captured once in `start_spawning()` — a swap in a combat stage dangles both, per live enemy. This is why character choice belongs in the safe house (a chamber the player walks up to), not in a combat stage. It is a rule, not a coincidence of where the chambers were placed.
- Player has two child controller nodes: **`AttackController`** and **`PowerUpController`**.
- Current health lives in `GameStateGlobal` (registered via `register_player()`). `PlayerBase.take_damage()` refuses the hit when the player is dead, when `is_combat_allowed()` is false or while `ENEMIES` is held; otherwise it calls `GameStateGlobal.apply_damage()`.
- **The overhead `HealthBar` and `HealthLabel` hide in `EXPLORATION`** (`scripts/health_bar.gd`, `scripts/health_label.gd`): in the safe house health does not matter, and a bar over the head reads oddly there. Each connects to `GameStateGlobal.state_changed` **and applies the current state in its own `_ready()`** — a signal only reports *transitions*, and the player is born in the safe house with the mode already declared by `StageConfig` in `_enter_tree()`, so no transition would ever arrive (same lesson as the Barrier's `_reconcile_phasing()`). The condition is the **specific state**, never `is_combat_allowed()`, which is also false in `PAUSED` and `UPGRADE` — hiding health when you pause would be wrong. Invisible is not disabled: `HealthBar._process()` keeps animating behind it (cheap). The label's damage blink writes `modulate`, not `visible`, so the two never collide. The label shows health **truncated** (98.7 shows "98", not "99") — deliberate, common in games — **but never "0" while the player is alive**: with health > 0 it shows at least "1" (`maxi(1, int(current))`), the same rule as the bar, which with health > 0 always paints at least 1 px. Before, 0.37 health showed "0" on a living player. If a third element or a second state (`DIALOGUE`, `CUTSCENE`) needs the same rule, centralise it then.
- Armor from `PowerUpStatsGlobal.get_armor_damage_reduction()` is applied before forwarding damage.
- Follows the **feet origin + BodyCenter** convention: see *Entity anatomy*.
- **New character checklist** (for a scene using `player_character.gd`):
  - **The script fails without these:** `Sprite2D`, `AnimationPlayer` (animations `idle`, `walk`, `attack`, `walk_attack`), `Hurtbox` and `AttackController`, all found by fixed path.
  - **Errors or no function without these:** group `Player` on the root; `PowerUpController`, which `LoadoutBar` requires.
  - **Degrades with a warning without these:** `BodyCenter`, `AttackPositionRight/Left`, `Hurtbox` in the `PlayerHurtbox` group.
  - **Visual and calibration:** root configured for Y-sort (`z_index = 2`, `y_sort_enabled = true`), `primary_attack_id` on `AttackController`, `HealthBar` and `HealthLabel`.
  - **Test tools:** `TestPowerups` and `TestAttackUpgrades` (see *Debug and test systems*).
