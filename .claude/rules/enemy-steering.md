### Enemy inter-enemy avoidance — Context Steering
Inter-enemy avoidance is **context steering** (Reynolds/Fray family), not RVO. The `NavigationAgent2D` is used **only for pathfinding** (the wall-aware `base_dir`) — **its RVO avoidance no longer exists in this project: the code path was deleted, not disabled.** **`steering_enabled` defaults to `true`** in `EnemyBase` — steering is the game standard, so enemy scenes no longer set it; since Godot omits properties equal to the script default, its **absence from a `.tscn` means ON, not off**. Setting it `false` now means "walk straight along the route, dodging nothing", a comparison switch, not a second avoidance mode.

- **Why not RVO:** ORCA slowed enemies to a near-zero creep when circling a stationary enemy to reach the player — it picks the collision-free velocity closest to the desired one, and heading straight into a neighbor that is a slow forward crawl, not a full-speed lateral detour. No RVO param fixed it (`time_horizon`, `avoidance_priority`, `radius`, `max_speed`). Root cause: RVO only **deflects** the desired velocity, it can't **re-route**. Context steering preserves full speed and steers tangentially around blockers.
- **RVO is GONE, and with it an asynchronous frame path.** Removed: `_avoidance_pending` / `_pending_delta` / `_pending_pos_before`, the `_on_velocity_computed()` callback, the `velocity_computed` connection, the `elif` branch in `base_move` that called `set_velocity()`, and the six avoidance-only properties stored on each enemy's `NavigationAgent2D` (`radius`, `neighbor_distance`, `max_neighbors`, `time_horizon_agents`, `max_speed`, `avoidance_priority` — all six are read *only* by the avoidance system, `max_speed` included, so removing them changes no pathfinding). **The real gain is not the line count: movement now always finishes in the same physics frame.** With RVO, `base_move()` merely *declared* a desired velocity and the frame ended without moving; `move_and_slide()` ran later inside the server's callback, which is why a flag existed to discard answers that arrived after knockback, a stop, or death. `_finish_movement()` existed only to be callable from those two entry points and was inlined back into `_physics_process()`. **Reverting is no longer an Inspector toggle** — it would mean rewriting that async path. Do not treat `avoidance_enabled` on an agent as meaningful: nothing reads the velocity it would compute.
- **There is no PRIORITY between enemies today, and RVO had one.** `_steer_direction()` is symmetric and egoless: every neighbour is an equal obstacle and nobody yields. RVO's `avoidance_priority` made the low-priority agent absorb more of the detour. Three routes exist if a future enemy should get right of way, cheapest first, and any of them would be a *preference*, never RVO's collision-free *contract*: **(a)** `steer_block_min_interest` is already a per-enemy "how soon do I give up and queue" axis — crude, calibratable today, zero code; **(b)** **asymmetric clearance** — the neighbour loop currently measures every neighbour's blocked arc with **self's** `steer_enemy_clearance`; reading the **neighbour's** value instead turns it into "how much room I demand others give me", so a boss carves a wide arc in everyone else's map while barely deviating itself (one changed read plus a second `@export` to separate the two roles, still O(neighbours)); **(c)** **graded danger** — danger is binary `0/1` today, so `min_danger` is 0 or 1 and selection is "highest interest among the free slices"; real weighting needs continuous danger and a combined score, which recalibrates the meaning of `steer_block_min_interest`. Prefer (b).
- **How it works** (`_steer_direction`): samples `steer_slice_count` slices around the enemy. Each slice gets an **interest** (alignment with `base_dir`, the path toward the player) and a **danger** (0/1). Enemy danger = angular occupancy: a neighbor at distance `d` blocks the arc of half-width `asin(steer_enemy_clearance / d)`, so gaps wider than a body stay open and the enemy threads them. Wall danger = one raycast per slice against layer 1 up to `steer_wall_clearance`. It picks the clearest slice with the highest interest and moves at **full speed**; open field (no neighbor, or none blocking a slice) returns `base_dir` directly (smooth, straight).
- **Wall perception is gated by enemy proximity (non-obvious):** the whole deviation logic — **including the wall raycasts** — only runs when a neighbor is within `steer_detect_radius`. A **lone** enemy short-circuits to `base_dir` and the `NavigationAgent2D` path alone handles walls. So `steer_wall_clearance` is a **tie-breaker while dodging a neighbor** (it excludes wall-pointing slices when an enemy is boxed in by enemy + wall), **not** a general wall-distance keeper. (Making it always-on would need running the wall pass without a neighbor + a gradient repulsion — future work.)
- **"Wait" state** (`steer_block_min_interest`): if even the best clear slice does not point reasonably toward the player (even one close neighbour ahead can cause it), `_steer_direction` returns `Vector2.ZERO` and the enemy **holds position** — forming a natural queue / outer ring until a slot opens. With no free slice at all it does not wait: it takes the most aligned one and the colliders hold it. Held `velocity = 0` → IDLE via the existing state machine; the attack pose is still decided **solely by `attack_distance`** (untouched).
- **Colliders stay ON** (layer 3): they enforce final spacing and are what make knockback **chain-transfer** work (`handle_knockback_transfer` reads `get_slide_collision` = physical contact). Knockback itself **bypasses steering** (its own early branch in `base_move`).
- **Both periodic per-enemy systems are staggered, and for the same reason.** Beyond `steer_update_interval`, the `path_timer` gets a random first cycle (`start(randf() * path_recalc_interval)`; the Timer returns to `wait_time` afterwards, so the interval is unchanged — only the phase). Without it, enemies born in the same frame — and spawning happens in **bursts**, whenever the budget crosses `minimal_budget` — keep phase-locked timers and repath together forever. Measured: a real path recomputation costs **~370 µs** while the per-frame `get_next_path_position()` read is ~4 µs, so a synchronised group turns into a periodic multi-ms spike in a single frame. The initial route does not depend on this timer (`_setup_base()` calls `makepath()`, and `SpawnManager` calls it again after positioning).
- **`path_recalc_interval` is the cheapest navigation lever, and it has a floor.** Cost ≈ (repaths/s × ~370 µs) + (enemies × 60 × ~4 µs); only the first term follows the interval, so raising it past ~1 s buys little while degrading responsiveness. Enemies reacting with a slight delay reads as *organic*, not broken — the steering still corrects direction every frame, so the lag only shows on long map curves.
- **Cost / scale** (massive-horde game): `_steer_direction` is amortized by three things — **staggering** (`steer_update_interval`: recompute the direction once every N frames, staggered per instance, move every frame from cache), a **spatial grid** (`GRID_CELL_SIZE`, rebuilt once per physics frame and shared; each enemy queries only nearby cells → O(N) instead of O(N²)), and a **wall-danger cache** keyed by position (walls are static → re-raycast only after the enemy moves more than a few px).
- **Calibration** (per enemy, Inspector — `steer_*`): `steer_detect_radius` = perception trigger (a neighbor within it turns the deviation logic on). `steer_enemy_clearance` (enemy spacing) and `steer_wall_clearance` (wall distance) are **independent**. Normally keep `steer_enemy_clearance ≤ the physical contact distance` (sum of the two colliders) so steering complements physics and enemies **queue** rather than fight for extra room in corridors. Higher `steer_block_min_interest` = "wait"/queue sooner (helps corridors) at the cost of enemies giving up access more easily.
