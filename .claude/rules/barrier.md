**`entities/stage_parts/barrier.tscn` + `scripts/barrier.gd`** — a one-way gate: the player can cross once, then it closes behind them and blocks the return; enemies are never blocked (see *Physics layers*). Size is set in the Inspector as `length_tiles` (not px), so it's always grid-aligned. Direction detection compares which side of a **local** axis the player entered/exited an `Area2D` — crossing all the way through closes it, backing out does not — and rotating the scene redirects it (no separate scenes per direction). It is **not** part of Y-sort and needs no navmesh re-bake (enemies pass through freely). `starts_open` (default `true`) lets a barrier be placed already closed; the initial state is applied **directly** in `_ready()` (collider + frame), never by calling `close()`, which would play the raise animation on scene load. Close/open SFX play through `AudioManagerGlobal.play_sound_2d()` (the project-wide pooled SFX path — no dedicated `AudioStreamPlayer2D` node in the scene), same as everything else; `close_sound`/`open_sound` are still plain `AudioStream` exports dragged in via the Inspector.

**Enemies crossing a closed Barrier turn semi-transparent** (`EnemyBase.set_phasing()`, export `phase_alpha`), driven by `EnemyPhaseSensor`'s `body_entered`/`body_exited`. Because signals only report **transitions**, `close()`/`open()` call `_reconcile_phasing()` to apply the new state to enemies **already** overlapping — that reconciliation is required, not optional. (A polling variant was tried while chasing a bug whose real cause turned out to be `flash_red` overwriting `modulate`; once that was fixed, signals proved sufficient and the polling was reverted as unjustified complexity.)

**Rotating a `@tool` scene without rotating its artwork:** `barrier.tscn`'s art must stay upright even though the whole scene rotates to redirect the passage. A single stretched `TextureRect` (`stretch_mode = Tile`) can't do this — rotating the container rotates the tiling pattern too, since shape orientation and texture orientation are baked into the same quad. The fix: the visual is a **grid of individual unrotated `Sprite2D` tiles** (`length_tiles × thickness_tiles`, one 16×16 texture each), regenerated by `_apply_size()` inside a plain `Tiles` container node. Each tile's rotation is countered so its *global* rotation stays `0`, while its *position* still inherits the parent's rotation (so tiles correctly line up along a rotated corridor) — position and orientation are independent, so only orientation needs cancelling.

**`lock_visual_rotation`** (export on the root, group *Visual*): toggles that counter-rotation. `true` (default) keeps the art upright regardless of the scene's rotation — right for a gate whose tiles read the same from any angle. `false` lets tiles inherit the parent's rotation normally, for a future object whose art should visually track its own orientation (e.g. a directional damage barrier).

**Frame-by-frame animation drives N tiles at once, so it's a method track, not a value track**: because the tile count varies with `length_tiles`/`thickness_tiles`, `AnimationPlayer` can't key a fixed `NodePath:property` the way `major_heat.tscn` keys `Sprite2D:texture` — the tiles aren't fixed authored nodes. Instead, `close`/`open` use a **Call Method Track** invoking argument-less wrapper methods (`_frame_01()` … `_frame_12()`), each calling `_set_frame(n)`, which pushes `frames[n-1]` (an exported `Array[Texture2D]`) onto every tile currently in the grid. Argument-less wrappers exist for the same reason as `_enable_blocker`/`_disable_blocker`: picking a method for a keyframe is one click in the Animation panel; editing an argument on that keyframe is not.
